# Phase 0 Research: Today's Workout Screen

All Technical Context unknowns are resolved below. No open `NEEDS CLARIFICATION`
items remain (the three spec clarifications from 2026-07-14 already settled
session-state source, rest-day behavior, and 409 handling).

## R1. How to expose current session state on the workout day

- **Decision**: Extend `WorkoutDaySchema` with a nullable `session` object
  (`id`, `startedAt`, `completedAt: nullable`) and map it in `GetWorkoutDay`.
- **Rationale**: `GetWorkoutDay.execute()` already calls
  `prisma.workoutDay.findUnique({ include: { exercises: {...}, sessions: true } })`,
  so the session data is **already fetched** — it is simply stripped by the
  response schema. `StartWorkoutSession` blocks a second session per day
  (`findFirst` by `workoutDayId` → `SessionAlreadyStartedError`), so a day has
  **0 or 1** session. Exposing a single `session` (not an array) matches reality
  and keeps the client trivial.
- **State derivation**: `session == null` → not started; `completedAt == null`
  → in progress; `completedAt != null` → completed.
- **Serialization note**: Prisma returns `Date` objects; `completeWorkoutSession`
  already converts with `.toISOString()`. `GetWorkoutDay` must do the same for the
  mapped `session` because the schema field is an ISO datetime string.
- **Alternatives considered**: (a) separate `GET session` endpoint — rejected:
  extra round-trip, and the data is already loaded here; (b) derive from
  `consistencyByDay` on home data — rejected: it exposes booleans but **not** the
  `sessionId` required by the complete endpoint.

## R2. Backend contract change + client regeneration

- **Decision**: Edit `WorkoutDaySchema.ts` (+ `GetWorkoutDay.ts`), start the
  backend, then run `cd packages/web && npx orval` to regenerate
  `src/lib/api/fetch-generated/index.ts`.
- **Rationale**: Project rule — backend is the single source of truth for API
  shapes; the web client is generated by Orval from `/openapi.json`. Hand-editing
  the generated file is forbidden.
- **Alternatives considered**: manually adding the field to the generated client
  — rejected (violates non-negotiable rules; drifts from OpenAPI).

## R3. Calling mutations from a client component

- **Decision**: Use Next.js **Server Actions** (`actions.ts` with `'use server'`)
  that wrap the generated `startWorkoutSession` / `completeWorkoutSession`, invoked
  from a client action island; re-derive state with `router.refresh()`.
- **Rationale**: The generated client uses `customFetch`, which imports
  `next/headers` `cookies()` and is therefore **server-only** — it cannot run in a
  browser client component. Server Actions keep cookie/session forwarding intact,
  keep business logic out of the component, and avoid inventing a parallel
  client-side fetch path.
- **Alternatives considered**: (a) Route Handlers proxying the API — rejected:
  more boilerplate than actions for a same-origin mutation; (b) calling the
  backend directly from the browser with a new fetch wrapper — rejected: duplicates
  auth/cookie logic and bypasses the generated client.
- **Follow-up**: read `node_modules/next/dist/docs/` Server Actions + `redirect`
  pages before implementing (per `packages/web/AGENTS.md`).

## R4. 409 "already started" reconciliation

- **Decision**: In the start action, detect the `409` /
  `SESSION_ALREADY_STARTED_ERROR` response, return a `conflict` result; the island
  shows an informational toast and calls `router.refresh()` so the server
  re-derives the true state (in progress / completed).
- **Rationale**: Matches spec clarification + FR-018; self-heals stale UI without
  a blocking error.

## R5. Toast feedback (sonner)

- **Decision**: Add `sonner` to `packages/web`, create the shadcn `sonner.tsx`
  Toaster wrapper, mount `<Toaster />` once in `src/app/layout.tsx`. Use
  `toast.success` / `toast.error` / `toast.info` from the action island.
- **Rationale**: Spec requires toast feedback; no toast primitive exists. sonner
  is the shadcn-standard and integrates with the existing cva/clsx/tailwind-merge
  setup. Single mount avoids duplicate toasters.
- **Alternatives considered**: custom toast context/portal — rejected: more code,
  weaker a11y, inconsistent with shadcn conventions.

## R6. "Finalizado!" success badge

- **Decision**: Add the shadcn `badge` component with a `success` variant; add a
  `--success` / `--success-foreground` token to `globals.css` if none exists,
  sourced from the Figma completed-state node.
- **Rationale**: Constitution forbids hardcoded colors; the app currently has no
  green/success token (only `--streak`, `--primary`, `--destructive`). A token
  keeps light/dark theming consistent. Badge is a local component (no npm dep).
- **Alternatives considered**: reuse `--primary` or `--streak` — rejected: not a
  success semantic; hardcoded green — rejected (violates token rule).

## R7. Pinned top card & bottom bar without overlap

- **Decision**: Page header `sticky top-0 z-40`; start card `sticky` beneath the
  header (`top-[header-height] z-30`); complete bar `fixed left-0 right-0 z-40`
  offset above the fixed bottom nav; add bottom padding to the scroll content so
  the exercise list clears the bar. Exact pixel offsets taken from Figma.
- **Rationale**: The `(main)` layout already renders a `fixed … bottom-0 z-50`
  `BottomNav` with `pb-28` spacer on the page wrapper. The complete bar must sit
  above that nav (higher `bottom`, lower `z` than the nav's rounded top) and never
  overlap it (FR-011); the start card must not cover the header (FR-010).
- **Alternatives considered**: `position: fixed` for the start card — rejected:
  harder to keep below a sticky header on small screens; sticky composes cleanly.

## R8. Redirect guards (invalid / rest day)

- **Decision**: In the server component, `await getWorkoutDay(...)`; if
  `status !== 200` **or** `data.isRest` → `redirect('/')` before rendering.
- **Rationale**: FR-014 + rest-day clarification. Mirrors the home page's own
  status-based redirect pattern. `getUser()` / `proxy.ts` already cover the
  unauthenticated case.
